## 四、发现并修复的小程序端缺陷（4 处）

### 4.1 【高】`reviewed` 终态未锁定，填报页仍可编辑提交（交接 A4 未落地）

- **现象**：教师表单 `status=reviewed` 时，填报页 `readonly=false`，底部仍显示「提交填报」、行内仍有「删除 / ＋新增明细行」；首页入口文案为「查看/修改填报」。
- **证据**：页面数据 `{status:"reviewed", readonly:false, lockHint:""}`；后端此时返回 `409 STATE_CONFLICT`「该征订单已通过审核，不能再次提交；如需修改请联系教材室驳回后补正」——用户改完行会被打回、改动白丢。
- **修复**：
  - `pages/teacher-order-form/teacher-order-form.js`：`applyReadonly()` 将 `reviewed` 视为终态，`readonly=true` + 提示「已通过审核，如需修改请联系教材室驳回后补正」；
  - `pages/home/home.js` + `home.wxml`：入口按钮文案改为按状态计算（`去填报` / `去补正重提` / `查看填报` / `查看/修改填报`）。
- **回归**：填报页显示「· 只读」、底部按钮「已锁定」、增删行入口消失；首页显示「查看填报」。

### 4.2 【高】阻塞弹窗的「已清空」标记永不复位 → 换账号 / 新通知后不再弹

- **现象**：确认过一轮通知后，模块级 `sessionCleared` 在整个 app 生命周期内不再复位。表现为：① 退出登录换账号，新账号的阻塞通知**永远不弹**；② app 常驻期间后端新发通知，回到小程序也不弹。
- **证据**（修复前）：
  - 教师确认完通知 → 退出 → 学生登录；学生此时有 1 条未确认通知，但弹窗组件 `show=false`，且该时间窗内**后端日志零次** `/notice/unconfirmed` 查询（请求根本没发出）；
  - 手动 `ensureFetch(true)` 后弹窗立即正常显示，证明接口与组件逻辑无误，问题在早退判断。
- **修复**：把布尔标记换成 `clearedKey = 用户 id + 前台纪元`（`app.onShow` 递增 `noticeEpoch`）：
  - 换账号 → 键不同 → 重新拉取；
  - 回到前台 → 纪元递增 → 重新拉取（弹窗为主触达通道，必须能收到新通知）；
  - **空队列不再置位**（空 ≠ 用户已确认），只有「展示的队列全部确认完」才置位，从而保留 T4.1「6 条未确认只弹 5 条、确认完放行、第 6 条不阻塞」。
- **回归**：换账号后教师弹窗正常弹出；`onShow` 后进入页面重新拉取并弹出新通知。

### 4.3 【中】`reviewed` 表单的审核备注被显示成「驳回理由」

- **现象**：教师「提交记录」列表对**已通过**的表单显示「驳回理由：e2e」。
- **根因**：后端 `TeacherOrderService` 在 `action=pass` 时也会把 `reason` 写入 `review_note`（它是**审核备注**，非驳回理由），而 `teacher-records.wxml` 仅按 `reviewNote` 非空判断。
- **修复**：`teacher-records.js` 增加 `reviewNoteText`（仅 `rejected`/`rejected_auto` 时透出），模板改用该字段；与 `buildTrack`/`home.js` 的既有门禁口径一致。
- **回归**：已通过记录不再出现「驳回理由」，轨迹仍为「…→ 结果 · 审核通过」。

### 4.4 【中】`GET /api/student/orders` 无调用方，「我的记录」功能缺口

- **现象**：`api.student.orders()` 已封装但**全仓无调用点**；学生首页「我的征订记录」入口仅跳到「我的」页，而该页无任何选购记录区。`docs/08` 计划（§3.1 页面清单第 4 行、§5.3、验收项 T2.5）明确要求由 profile 页消费该端点。
- **修复**：`pages/profile/profile.js` 新增 `loadStudentOrders()`（学生身份时拉取），`profile.wxml` 新增「选购记录」区（学期 / 状态 / 明细行数 / 册数 / 归属快照 / 提交时间），并注明「历史学期仅提供汇总，本学期明细与金额见选购页」（对齐 API.md §3.7 已知缺口）。
- **回归**：「我的」页显示 `2026-2027学年秋季学期 / 已提交 / 明细 1 行 / 共 1 册 / 计算机学院 · 软工2023-1 / 提交于 2026-09-22 12:39`，与 `student/orders` 一致。

> 修复后 19 个端点**全部有调用方**（此前 18/19）。

## 五、后端侧：仅报告，未改代码

联调中未发现后端接口错误、返回格式不符或逻辑异常。以下为**文档/环境**层面的待补项，不影响小程序运行：

| 级别 | 项 | 说明与建议 |
|------|----|-----------|
| 文档 | `POST /api/admin/notice/tasks` 的 `targetRoles` 格式未写明 | 契约文档只写 `{title,content,targetRoles?}`，按字面传数组 `["STUDENT"]` 会得到 `400 PARAM_INVALID`；实际 DTO 是**逗号分隔字符串**（`NoticeTaskCreateRequest` 注释：「逗号分隔角色码」）。建议 API.md §3.11 补注格式与示例。小程序不消费该端点，无影响 |
| 文档 | `GET /api/student/orders` 无金额字段 | 摘要端点只返回 `itemCount`/`totalQuantity`，因此「历史学期金额合计」无法呈现；小程序已按「历史仅摘要」降级并在界面说明。若产品要求历史金额，需后端补字段 |
| 环境 | 共享 dev 数据库会被其它测试影响 | 联调期间出现非本次创建的 `[IT] 联调通知` 任务（id 3/4），把当时 active 的通知任务挤掉，导致一次弹窗验证失真（当时学生队列确实为空，属正确表现）。后端集成测试（`-Dmysql.local.enabled=true`）与手工联调共用同一 MySQL 实例，建议联调时避免并行跑测试套件 |

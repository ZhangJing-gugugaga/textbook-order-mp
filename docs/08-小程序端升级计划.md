## 1. 范围与角色边界

### 1.1 客户端形态（沿用锁定决策 E1-A）

保留现有原生小程序（微信原生 + 无第三方依赖），在其基础上改造；不做 uni-app 迁移。Web 端独立 Vue 3 应用，两线共用同一套后端 API。

### 1.2 角色边界（D1 / G3 定论）

| 角色 | 小程序 | 说明 |
|---|---|---|
| 学生 STUDENT | ✅ | 选书 + 提交 + 记录 |
| 任课老师 TEACHER | ✅ | 我的课程 + 填报 + 补正 + 记录 |
| 超管 ADMIN / 秘书 SECRETARY / 供货商 SUPPLIER | ❌ | 登录后提示「该身份请使用 Web 端」，提供退出登录 |
| 多角色（如教师+学生） | ✅ | 「我的」页提供切换身份（`POST /api/auth/switch-role`）；切换到非师生身份时按上一行处理 |

落地页按**权限码**判定（不写死角色名，对齐 02 §3）：

```
permissions 含 'order:form:submit'    → 教师首页（我的课程）
permissions 含 'student:order:submit' → 学生首页（征订任务）
两者都有 → 以 /api/me 的 currentRole 为准（「我的」页可切换）
都没有   → 「该身份请使用 Web 端」+ 退出登录
```

### 1.3 教师端功能边界（MP7 默认值）

| 能力 | 小程序 | 依据 |
|---|---|---|
| 我的课程 / 填报（含字段审查回显 + 补正入口 + correctDeadline + 关窗锁定） | ✅ | 主链路 |
| 我的提交记录（历史学期 + 明细 + 状态轨迹） | ✅ | 主链路 |
| 异动申请（`/api/teacher/change`） | ❌ **V1 仅 Web** | MP7 默认；写入本节以免验收争议 |
| 导出 | ❌ | 无对应权限，后端亦不向教师开放 |

### 1.4 「Web 与小程序功能一致」的边界定义（X6 销项）

02:134/142 的「功能一致」在本计划中**收窄为**：**学生选购主链路**（清单 → 勾选 → 数量 → 提交覆盖 → 记录）与**教师填报主链路**（课程 → 明细 → 字段审查 → 补正 → 记录）两端口径一致，含错误文案与交互约束（一人一本提醒、提交确认小字、关窗锁定）。

**明确不一致项**（不算偏离验收）：异动申请、全部导出、通知管理、组织/账号/学期/教材库/统计管理功能仅 Web。

### 3.3 `utils/request.js`（契约消费层）

**响应包络（冻结契约）**：一律 `{code, message, data}`，`code` 为**字符串**，成功为 `"0"`；`message` 成功时省略，`data` 为 null 时省略。

```js
// 分流规则：以 code 为准，HTTP 状态兜底（API.md §1.2）
// 1) HTTP 2xx 且 body.code === '0'  → resolve(body.data)
// 2) HTTP 204 或空 body            → resolve(null)   ← /api/notice/{taskId}/confirm 为 204 无 body
// 3) 其余                          → reject({ code, message, httpStatus, data })
```

- 请求头：`Authorization: Bearer <accessToken>`、`Content-Type: application/json`、`X-Device-Id: <deviceId>`（refresh 轮转会话语义用，见 §3.4）。
- 超时 15s；超时/断网归一为 `code: 'NETWORK_ERROR'`，文案走统一提示。
- **不实现**：分页封装（MP 消费的列表端点均返回**裸数组**，非 `PageResponse`；仅未来 `/api/notice/mine` 分页，见 §4.3-G2）。
- 并发：微信 `wx.request` 默认并发上限 10，页面按需限流（同时最多 5 个在途），避免 `request:fail` 并发拒绝。

### 3.4 `utils/auth.js`（会话层，MP10 默认值）

| 项 | 规格 |
|---|---|
| 令牌参数 | access **15 分钟**（`expiresIn:900`）；refresh **7 天**，**轮转**（旧作废发新） |
| Storage 键 | `tx_auth = { accessToken, refreshToken, deviceId, expiresAt }`；`tx_me`（`/api/me` 缓存，仅用于首屏渲染，进入页面后重取） |
| deviceId | 首次生成随机串持久化（`tx_device_id`），随 login / refresh / switch-role 上报 |
| 401 `TOKEN_EXPIRED` | **单飞 refresh**：首个 401 发起 `POST /api/auth/refresh {refreshToken}`，其余 401 请求**排队等待同一 Promise**；成功后重放原请求（每请求最多重放 1 次，`_retried` 标记防递归） |
| refresh 自身 401 / `REFRESH_INVALID` | 清 token → 提示「登录已过期，请重新登录」→ 跳登录页 |
| `ACCOUNT_DISABLED` | 清 token → 提示「账号已停用，请联系教材室」→ 跳登录页（停用用户下一次请求即被踢） |
| 403 `FIRST_LOGIN_REQUIRED` | **不跳登录页**，进入首登流程（§5.1） |
| 冷启动恢复 | 读 `tx_auth` → 有 refreshToken 则直连业务接口，401 走单飞 refresh；refresh 失败才跳登录页。**修复 MVP P3 #8（有会话仍显示登录页）** |
| 退出登录 | 尽力调 `POST /api/auth/logout`（失败忽略）→ 清 `tx_auth`/`tx_me` → 跳登录页 |

**两个必须实现的细节（本计划新发现，见 §4.4）**：

- **N5 · refresh 会重置 `currentRole`**：服务端 `AuthService.refresh()` 把 `currentRole` 重新取 `roles[0]`。多角色用户切换身份后发生静默 refresh，身份会回退。→ **refresh 成功后重取 `/api/me`**，若 `currentRole` 与本地不一致，用返回的 `currentRole` 覆盖本地（或重新 `switch-role`），不得静默沿用旧值。
- **N4 · 类型不一致**：`mustChangePassword` / `firstLoginVerified` 在 `AuthResponse` 是**布尔**，在 `/api/me` 是 **0/1 整数**。→ 在 `auth.js` 内统一归一为布尔后再交给页面。

### 3.5 `utils/store.js` 迁移方案（07 §4 事实核对销项）

**事实**：`store.js` 是**同步** Storage 实现，页面同步调用（`home.js:31,66-69`、`order.js:39-44` 等），全仓 **69 处代码调用点 / 11 个文件**。02:171「保持函数签名，内部 Storage → request」**在技术上不成立**——改成 API 后签名必变异步。

**替代方案**：

1. `store.js` **整文件删除**，由 `utils/api.js` 承接；不保留兼容层（避免同步语义残留）。
2. 调用点全部改为 `await`：`onLoad`/`onShow` 改为 `async` 或在内部 `.then`；每个页面引入统一的 `loading`/`error`/`empty` 三态渲染。
3. **聚合形状由页面自行组合**（服务端不再提供 MVP 的 `{orderId:{userId:{...}}}` 嵌套结构）：例如 MVP `profile.js:33` 的 `subs[o.id][session.id]` 改为 `GET /api/student/order`（当前学期单条）；`home.js:72` 的管理端提交计数**整体删除**（admin 页退场）。
4. 首启迁移：检测到 `tx_seeded_v1` 等 MVP 遗留键 → **清空全部 `tx_*` 业务键与旧 `tx_session`**，强制重新登录一次（MVP 数据为设备本地演示数据，无迁移价值）。
5. 验收：`grep -rn "require.*store" pages/ utils/` 结果为 0。

### 3.6 联调方式（MP11 默认值）

- **直连后端，不引入 MP mock 层**（契约已冻结、后端已交付）。
- 本地：`http://localhost:8080/api`（后端 `./mvnw spring-boot:run`，`local` profile 自动建表 + 种子）；开发者工具关闭域名校验。
- 试运行：`https://moonzj.com/api`（需后端已部署 + 合法域名已配）。
- 后端不可用期间：**页面按空态 + 网络错误提示渲染**，不得回退到本地假数据。

## 5. 逐页设计要点

### 5.1 登录与首登（X3 / X4 / Z4 / MP3 销项）

**流程（按后端已交付实现，02 §3/§8 的旧口径作废）**：

```
① 输入 学号/工号 + 密码 → POST /api/auth/login
② 响应 mustChangePassword=false 且 firstLoginVerified=true → 按权限码落地（§1.2）
③ 响应 mustChangePassword=true → 进入首登流程（不可跳过）：
   ③.1 首登校验：首选 wx.login → wxCode → POST /api/auth/first-login/verify {wxCode}
       （换取并绑定 openid；顺带完成 openid 绑定，见 §4.3-G4）
       wxCode 失败/环境未配 → 降级为「手机号后 4 位」输入 → {phoneTail}
   ③.2 校验通过 → 改密页：PUT /api/me/password {oldPassword, newPassword}
       规则：8–64 位且含字母和数字（服务端 PASSWORD_POLICY 兜底）
   ③.3 改密成功返回新令牌 → 落地
④ 任何业务接口返回 403 FIRST_LOGIN_REQUIRED → 回到 ③（兜底，防止绕过）
```

- **删除 02 §8:165 的「openid 仅推送用」表述**：openid 的用途是**首登校验绑定 + 订阅消息发送前置**（X4 销项）。
- 登录错误文案映射：`LOGIN_FAILED`「账号或密码不正确」、`ACCOUNT_LOCKED`「账号已锁定，请稍后再试」（5 次失败锁 15 分钟）、`ACCOUNT_DISABLED`「账号已停用，请联系教材室」、`RATE_LIMITED`「操作过于频繁，请稍后再试」。
- 演示账号快捷填充按钮**保留**（教师/学生各一），文案更新为含密码的种子账号（见 §10.3）。
- 首登校验与改密**先于**通知弹窗（02 §3.3 规则 1）：未改密不拉取业务数据。

### 5.3 学生选购页（X1 / X7 / X8 / MP4 / MP9 销项）

| 项 | 规格 |
|---|---|

### 5.4 教师端三页

#### 5.4.1 我的课程（`teacher-courses`）

- 数据：`GET /api/teacher/my-courses` → 已按班级分组，直接渲染「班级 → 课程」两级列表。
- 空态：「暂无任课关系，请联系教材室导入」（征订范围 = 已导入的 `teacher_course`，W17）。
- 点课程 → 进入填报页并定位该 课程×班级 行。

#### 5.4.2 填报页（`teacher-order-form`）——**与 MVP 学生勾选页模型完全不同（X5 销项）**

**明细模型 = 课程 × 班级 × 教材 × 数量**，不是勾选清单。UI 为**可增删的明细行编辑器**：

```
[班级 · 课程]  教材（选择器，检索）                数量   [删除]
软工2023-1 · 数据结构   《数据结构（第3版）》…     45    [×]
软工2023-1 · 软件工程   《软件工程导论》…          40    [×]
                                            [+ 新增明细行]
```

| 项 | 规格 |
|---|---|
| 加载 | `GET /api/teacher/order-form`（null → 空表单）；已提交/被驳回的表单回填明细 |
| 教材选择 | 调 `GET /api/teacher/textbook`（**待后端补，§4.3-G1**）；选择器需 keyword 检索 + 分页 + 空态；行内只读回显 `textbookTitle/isbn` 来自表单明细 |
| 课程×班级 取值 | 只能取自 `my-courses`（服务端校验 `COURSE_OWNER` / `CLASS_LINK`，前端用下拉约束） |
| 数量 | 仅校验 ≥1（**教师上限 = 班级人数，回退 999，无 9 的上限**——N7，不可复用学生页常量）；超限由服务端 `QTY_RANGE` 回显 |
| 提交 | `POST /api/teacher/order-form/submit`；覆盖语义（整单替换） |
| 字段审查回显 | 400 `FIELD_CHECK_FAILED`，`data=[{field,rule,message}]`，`field` 形如 `items[0].quantity` → **解析下标定位到行**，行内红字 + 顶部汇总「存在 N 项问题，请按提示修复后重新提交」；6 条规则：`REQUIRED` / `QTY_RANGE` / `BOOK_ACTIVE` / `COURSE_OWNER` / `CLASS_LINK` / `ISBN_FORMAT` |
| 补正入口（X8 销项） | `status ∈ {rejected, rejected_auto}` → 表单解锁 + 驳回理由（`reviewNote`）醒目展示 + 按钮文案「补正重提」；**展示 `correctDeadline` 及倒计时**（超期提交返回 409 `CORRECTION_EXPIRED`「补正窗口已过，请联系教材室」） |
| 关窗锁定 + 补正豁免（W4） | 窗口 closed 时：非被驳回表单 → 只读锁定；**被驳回表单在 `correctDeadline` 前仍可提交**（服务端 `@WithinWindow(Exemption.CORRECTION)` 放行）。前端不得用「窗口 closed」一刀切禁用——这是 Web 当前实现的缺陷，MP 不得复制 |
| 提交后状态 | 全通过 → `pending_review`「已提交，等待审核」；被驳回 → 展示理由 + 补正入口 |

#### 5.4.3 提交记录页（`teacher-records`）

- 列表：`GET /api/teacher/order-forms`（跨学期，含 `semesterName` / `status` / `itemCount` / `totalQuantity` / `reviewNote` / `correctDeadline`）。
- 明细：进入后按当前学期取 `GET /api/teacher/order-form`（当前学期单条）；历史学期明细端点**不存在**，V1 仅展示列表级信息（本计划明确边界，避免验收争议）。
- 无导出。

#### 5.4.4 审查状态轨迹口径（L11 / MP6 销项）

**与 Web 同口径：前端按 `status` + `submittedAt` / `reviewAt` 推导，不新增后端端点。** 把该口径写死在此以免验收时被要求「真实时间线」：

| 步骤 | 条件 | 时间取 |
|---|---|---|
| 提交 | 恒有 | `submittedAt` |
| 系统字段审查 | 恒有；结果取 `fieldCheckResult`（通过 N 项 / X 项未通过） | `submittedAt`（无独立字段，与 Web 一致） |
| 超管内容审核 | `status ∈ {pending_review, reviewed, rejected}` | `pending_review` → 待处理；`reviewed`/`rejected` → `reviewAt` |
| 结果 | `reviewed` → 通过；`rejected` / `rejected_auto` → 驳回 + `reviewNote` | — |

### 5.6 阻塞弹窗通知组件（X2 / Z5 / MP5 / MP12 销项）

```
登录成功 / 进入任一页面（loaded 标志防重复）
→ GET /api/notice/unconfirmed
→ 失败 = fail-open（放行进入，下次进入重查）
→ 有未确认 → 自绘居中阻塞 Modal，按 createdAt DESC 取最新 5 条（POPUP_QUEUE_MAX）排队
→ 逐条展示，点「收到」→ ① wx.requestSubscribeMessage（在点击回调内）→ ② POST /api/notice/{taskId}/confirm
→ 确认失败 → 保持弹窗阻塞 + 错误提示（不出队）
→ 展示的 5 条全部确认完 → 放行
```

| 项 | 规格 |
|---|---|
| 队列上限 | **保留最新 5 条**（`config.POPUP_QUEUE_MAX`，与后端 `notice.popup_queue_max` 默认值一致）；**确认完展示的 5 条即放行**，其余在「我的」页可查（X2 销项：第 6 条起**不阻塞**） |
| 组件 | 自绘居中 Modal（**禁用 `wx.showModal` 作为阻塞通道**）；单条展示 title + content + createdAt；进度文案「还有 N 条通知待确认」 |
| `roundStopped=true` | 展示「（该通知已停止重复推送，仍需确认）」提示，**仍必须确认**（弹窗通道无轮次上限，Q7/W8） |
| 确认请求 | `POST /api/notice/{taskId}/confirm`，body 可选 `{subscribeResult}`；**返回 204 无 body**（N8，`request.js` 必须处理）；幂等，重复调用仍 204 |
| 容错 | `404 NOT_FOUND` / `409 STATE_CONFLICT`「通知任务已关闭，无需确认」→ 视为已确认，出队继续 |
| 与首登顺序 | 改密弹层**先于**通知弹窗；未改密不拉通知 | 
| **N3 风险** | `/api/notice/unconfirmed` 服务端**不按 targetRoles 过滤** → 教师可能看到学生向通知。MP 按「全量展示」实现（不假设角色定向）；如需修正由后端处理，不在前端过滤 |

### 5.7 窗口三态（§4 / MP4）

- 状态与倒计时**全部来自服务端**：`serverTime` 与 `windowEnd` 求差（不信本地时钟，PRD 功能 2）。
- `not_open`：「距离开始还有 X 天 X 时 X 分」；`open`：「本期征订将于 X 后截止」；`closed`：「本期征订已截止，可查看历史记录」。
- 提交/填报的硬门禁：`windowStatus === 'open' && channelOpen === 1`（**`channelOpen` 是第二道闸**，不可只看 `windowStatus`）。
- 教师被驳回表单的补正是**唯一例外**（§5.4.2）。

## 11. 订阅消息通道（X9 / Z7 / MP12 销项）

| 项 | 结论 |
|---|---|
| **定位**（按 W5，02 §5:93 旧口径作废） | **弹窗为主触达**；订阅消息仅为**已授权学生的额外提醒**。一次性订阅「一次授权一条」，未确认者≈未授权者，重发对目标人群基本无效 |
| 触发点 | **必须在「收到」点击回调内**调 `wx.requestSubscribeMessage`（**禁止进入即调用**——微信要求授权由用户点击触发，02:94「首次进入小程序时引导授权一次」技术不可按字面实现，本条为修正口径） |
| 上报 | `POST /api/notice/{taskId}/confirm` 带 `{subscribeResult:"accepted"|"rejected"}`（服务端仅记日志，不落库） |
| 通道前置 | 服务端只对 **`openid` 非空的学生** 发订阅消息（`NotifyService.sendSubscribe`：openid 为空 → 记 `unauthorized`）。故 **openid 绑定是通道前提** → 走 §4.3-G4 |
| 授权状态查询 | 微信不提供查询接口 → 「我的」页按 `openidBound` + 最近一次本地授权结果展示，**不承诺更细粒度** |
| **降级方案** | 模板类目在个人主体下不可报 / `WX_SUBSCRIBE_TEMPLATE_ID` 未配 → **纯弹窗 + `unauthorized` 名单线下兜底**；验收按此口径，不按「全量必达」 |
| 教师/秘书 | 仅弹窗触达（不保证必达，Q8） |
| 验收 | MP 侧 = 授权弹窗由点击触发 + 上报成功 + 降级路径可演示；通道统计属后端试运行验收 |

## 13. 本计划新发现（07 号文档未覆盖，均已给默认处置）

| # | 发现 | 证据 | 处置 |
|---|---|---|---|
| N1 | **openid 绑定入口唯一且被复用**：`POST /api/auth/first-login/verify {wxCode}` 是唯一绑定点，且**无「待改密」守卫**，登录后即可调用 | `AuthService.java:130-166`、`AuthController.java:38-42`、`MeController.java:50` | 复用为「绑定微信」入口（§4.3-G4）；需后端确认语义 |
| N2 | **订阅通道的 openid 前置**：服务端 `openid` 为空即记 `unauthorized`，不发订阅消息 | `NotifyService.java:381-395`、`WxMaClient.java:63-86` | 与 §11 联动：绑定失败 = 该用户订阅通道不可用，降级为弹窗 |

| `FIRST_LOGIN_REQUIRED` | 403 | 进入首登流程（**不跳登录页**） | 请先完成首登校验并修改初始密码 |
